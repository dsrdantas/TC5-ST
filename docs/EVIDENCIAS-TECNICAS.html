📊 SRE — Service Level Objectives

Definição Formal de SLI, SLO e SLA

Service Level Indicator (SLI)

Métricas observáveis que indicam o desempenho real do serviço.

SLI Definição Métrica Objetivo
Availability Taxa de requisições sem erro 5xx (1 - taxa_erros_5xx) × 100% ≥ 99.9%
Latência P95 Percentil 95 da latência de resposta histogram_quantile(0.95, latency) < 300ms
Taxa de Erro 5xx Requisições com status 500-599 rate(http_5xx_errors[5m]) < 0.1% por minuto

Service Level Objective (SLO)

Objetivo de desempenho que queremos atingir internamente.

SLO Objetivo Error Budget/Mês Justificativa
Availability ≥ 99.9% 43 min 48s de downtime Padrão para sistemas de doação não-financeiros
Latência P95 < 300ms 5% das requisições podem exceder Perceptível para UX de doação

Service Level Agreement (SLA)

Compromisso contratual externo com ONGs parceiras.

SLA com ONGs Parceiras
99.5%
Disponibilidade Contratada

Margem de segurança: SLO (99.9%) vs SLA (99.5%) = 0.4% de buffer

Burn Rate Alerts

Alert Condição Limiar Ação
SLOFastBurn Queima 14.4x o orçamento 2+ horas para esgotar PagerDuty + Self-Heal
SLOSlowBurn Queima 1x o orçamento 6 horas para esgotar Escalação SRE

🛡️ Segurança e Disaster Recovery

Performance Characteristics & Non-Functional Requirements (PCN)

RPO (Recovery Point Objective)

Quantidade máxima de dados que podemos perder em caso de desastre.

Componente RPO Método
RDS PostgreSQL 5 minutos Read-replica com streaming replication
DynamoDB < 1 segundo Global Tables (replicação nativa)
EBS Volumes 15 minutos AWS Backup snapshots
Application Code < 1 segundo ECR replicated

RTO (Recovery Time Objective)

Tempo máximo para recuperação após um desastre.

Passo Tempo Ação
1. Detectar failover 2 min Health check falha em CloudWatch
2. Promover RDS replica 3 min AWS RDS API call
3. Scale EKS DR 5 min Aumentar node group 1→3 nodes
4. Update DNS/ALB 1 min Route53 change
5. Verificar saúde 2 min Health checks pass
TOTAL RTO ~15 minutos

Padrão DR: Warm Standby (Skeleton)

Aspecto Primary (us-east-1) DR (us-west-2)
EKS Nodes 2-3 (production) 1 (skeleton)
RDS Primary database Read-replica (standby)
DynamoDB Active Global Tables Replica
SQS Active queue Separate (messages lost)
Custo mensal ~$235 ~$65

Estratégia de Failover

Fase 1: Detecção (Automática) ├─ CloudWatch detecta primary region outage ├─ SNS notifica on-call engineer └─ Alertmanager dispara CRITICAL Fase 2: Decisão (Manual) ├─ On-call verifica scope da falha ├─ Contata stakeholders (ONGs) └─ Aprova failover Fase 3: Execução (10-15 min) ├─ Promover RDS read-replica ├─ Scale EKS nodes (1→3) ├─ Update Route53 DNS └─ Sync ArgoCD Fase 4: Validação (2-5 min) ├─ Health checks pass ├─ Smoke tests executados └─ Stakeholders confirmam acesso

🔧 ITSM/AIOps — Incident Management Lifecycle

Ciclo de Vida de Incidentes

[1] DETECÇÃO ──→ [2] TRIAGEM ──→ [3] MITIGAÇÃO │ │ │ Prometheus rules On-call avalia Auto: workflow New Relic AIOps severidade real self-healing AWS Health Dashboard Cria warroom Discord Manual: runbook │ │ │ ▼ ▼ ▼ Alertmanager PagerDuty incidente Cluster opera │ │ ├─→ PagerDuty (ITSM) │ ├─→ Discord (ChatOps) │ └─→ GH Actions self-heal │ │ ▼ [4] COMUNICAÇÃO ←── [5] RESOLUÇÃO ←── [6] POST-MORTEM Status page externa SLO + Error Budget Doc blameless Email diretoria validacao Action items Discord time interno APM Service Map sai Schedule review Twitter / Instagram do vermelho

Fase 1: Detecção (0-2 min)

Fonte Tipo O que detecta
Prometheus PrometheusRules Métricas Erros 5xx, latência P95, pod crash
New Relic Applied Intelligence AIOps Anomalias comportamentais
AWS Health Dashboard Infra Falha regional/AZ na AWS
Velero Backup DR Backup diário falhou (RPO em risco)

Roteamento de Alertas (Alertmanager)

critical ──→ PagerDuty (cria incidente) + Discord (visibilidade) + GitHub Actions (self-heal) warning ──→ Discord apenas SLO burn ──→ PagerDuty imediato + Discord + Escalação SRE

Fase 2: Triagem (2-5 min)

SRE on-call recebe page do PagerDuty. Checklist rápido:

  1. Confirmar via Grafana — alerta é real?
  2. Verificar AWS Status Page — incidente regional?
  3. Olhar New Relic Service Map — qual componente é a causa raiz?
  4. Determinar severidade real (SEV-1/2/3)
  5. Abrir war-room no Discord
  6. Acknowledge no PagerDuty

Matriz de Severidade

Severidade Impacto Usuários Afetados RTO
P1 Total Todos (0% availability) 30 min
P2 Alta Parcial (Donation service down) 1-2 horas
P3 Média Funcionalidade degradada 4 horas
P4 Baixa Cosmético/UI Próximo sprint

Fase 3: Mitigação

🤖 Auto-Remediation: Webhook-receiver → GitHub Actions → self-healing.yaml → kubectl rollout restart → tempo total: ~3 minutos

Fase 5: Resolução

  1. Marcar como resolved em PagerDuty
  2. Atualizar status no Slack/Discord
  3. Agendar Post-Incident Review (24h)

Fase 6: Post-Mortem

  1. Reunião do time (24h após resolução)
  2. Timeline da falha + root cause
  3. Items de ação (correções)
  4. Atualizar runbooks
  5. Melhorar alertas/SLOs se necessário
